Reading and planning code

Seeing the shape first

Losing the high-level shape inside unfamiliar syntax — and the fix.

The syntax of a new language (bracket types, comma placement, quote matching) is dense enough on its own that it's easy to lose the big-picture structure of what the code is actually doing while fighting the small-picture detail of how to write it correctly. Both are real skills but they're not the same skill, and trying to hold both in mind at once at speed is what causes the "can't see the wood for the trees" feeling.

The fix that works: separate the two explicitly. Before writing any code, describe the structure in plain terms as nested containers — a big box, with a middle box inside it, with a small box inside that, and dividers inside the small box if needed. Get the shape right first, in words or a sketch, with no Python syntax at all. Only once the shape is settled, translate each box into its actual Python syntax one layer at a time. This maps directly onto the existing orange/outer, blue/middle, green/inner colour system already used in the notes for nested code — same idea, applied before code is written, not just after as a colour-coded explanation of code that already exists.

Reading and planning code

Top to bottom

Python runs top to bottom — a variable has to be created before the line that uses it.

Writing a calculation line before the input() line that fills the variable it depends on (e.g. total_price = items * price_per_item above an items = int(input(...)) line that comes after it) fails, because at the moment the calculation runs, items doesn't exist yet. Order isn't cosmetic — it's the sequence Python actually executes in. The fix is always the same: the line that creates a variable has to appear above every line that uses it.

Worth drilling deliberately, alongside the colon rule (block-openers only, never on a plain statement) — an exercise that tests both of these at once would be a useful thing to have.

What it looks like when it goes wrong.

total_price = items * price_per_item items = int(input("How many? "))
NameError: name 'items' is not defined

NameError almost always means one of two things, and they're worth telling apart because the fixes are different:

  • The name is spelled differently somewhere. items vs Items vs item. Python is case-sensitive and does not guess.
  • The name is defined, but below the line using it. Which is this case. The definition exists — it's just too late.

The diagnostic that separates them: search the file for the name. If it appears nowhere else, it's a typo. If it appears further down, it's an ordering problem.

The fix, and why it's not just "move the line up". Moving lines around until the error stops is guesswork. The reliable method is to read the line that failed and ask what it needs, then make sure every one of those things is created above it:

items = int(input("How many? ")) # needs: nothing price_per_item = 2.50 # needs: nothing total_price = items * price_per_item # needs: both of the above

Written in dependency order, the file reads as a sequence where every line is already supplied with what it uses.

The one genuine exception, so it doesn't confuse you later. Function bodies don't follow this rule, because a body doesn't run when it's defined — it runs when it's called.

def show_total(): print(total) # "total" doesn't exist yet — that's fine total = 100 show_total() # prints 100

This works. By the time show_total() is actually called, total exists. The rule is really "created before the line that uses it runs" — which for ordinary top-level code is the same as "created above it", but for function bodies is not.
