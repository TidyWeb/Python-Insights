Symbols and punctuation

Brackets — one symbol, three jobs

The same bracket symbol does different jobs depending on context.

  • {} — two unrelated jobs: building a dictionary ({"regular": 2.50}), or marking an insertion point inside an f-string (f"{price}"). Never both at once — whether it's Job 1 or Job 2 depends on whether it's sitting inside a string with an f in front of it.
  • [] — three jobs: building a list ([1, 2, 3]), indexing/key lookup glued onto an existing variable (menu["regular"], tools[0]), or slicing with a colon inside (tools[0:2]).
  • () — three jobs: calling a function (print(...)), grouping in maths for order of operations ((a + b) * c), or building a tuple (("Mon", "Tue")) — a list that can't be changed after it's made.

The rule for telling them apart: look at what's directly to the left of the bracket, and whether it's inside a string. A bare bracket starting a new value is creating something; a bracket glued onto an existing name is reaching into something that already exists.

The single test that covers all three symbols. Ask: is there a name glued to the left of this bracket, with no space?

tools = ["hammer", "saw"] # nothing glued left of [ → building tools[0] # "tools" glued left of [ → reaching in print("hello") # "print" glued left of ( → calling (2 + 3) * 4 # nothing glued left of ( → grouping

Glued to a name → you are doing something to that name (reaching in, or calling it). Standing alone → you are making a new thing. That one test resolves [, (, and { alike, which is why it's worth having as a single habit rather than three separate rules.

Why the same symbols got reused for different jobs. Not because Python is being awkward — because the language only has three bracket shapes on a standard keyboard and needed more than three jobs. There's no deeper logic connecting "build a list" to "look something up"; they share [] by necessity, not by meaning. Knowing that stops you hunting for a connection that isn't there.

Symbols and punctuation

[] does double duty

[] does double duty — it builds lists AND looks values up. {} only ever builds.

Square brackets are often taught as belonging to lists only, rather than as having two separate jobs. If that is how you first met them, this correction needs active repetition rather than a single reading.

{} — one job only: building a dictionary from scratch. staff = {"name": "Priya", "role": "manager"} — declaring a new dictionary and its contents. {} never means "go look something up," in any context, regardless of what's nested around it.

[] — two separate jobs, told apart by position:

  • Building, standing alone after =: tools = ["hammer", "saw"] — constructing a new list, same role {} plays for dictionaries.
  • Looking up, sitting directly after something that already exists: person["name"], tools[1], customers[0:2] — reaching into something already built and pulling a piece back out.

The rule that matters for lookups: whenever you're retrieving a value from a dictionary — building it, target-selecting inside it, putting the reticle on it — the bracket is always [], never {}, regardless of whether that dictionary sits alone or nested inside a list. The list wrapped around it changes nothing about this rule; it only adds one extra step beforehand (get to the right dictionary first), the lookup bracket itself never switches.

Read the outermost bracket

The outermost bracket tells you the container type — what's nested inside doesn't change it.

customers = [ {...}, {...}, {...} ] is a list — signalled by the outer [ ] — that happens to contain dictionaries. Slicing it (customers[0:2]) always hands back another list, even though each item inside that list is itself a dictionary denoted by { }. Don't let the bracket type of the contents override the bracket type of the container — read from the outside in to identify what you're actually holding, then look inside to see what it's made of.

Colons open blocks

Colons only belong on lines that open a new indented block.

if, elif, else, for, while, def — these all end their line with : because they're announcing "an indented block follows this line." A plain assignment (final_price = discount) is not opening a block, so it never takes a colon. If a colon shows up on a line that isn't one of those keyword lines, it's a stray character, not a rule being followed.

The complete list, so there's nothing to guess at. Only these open a block and therefore take a colon:

if · elif · else · for · while · def · class · try · except · finally · with

That's the whole set. Anything not on that list never takes one.

What it looks like when it goes wrong.

final_price = discount:
SyntaxError: invalid syntax

SyntaxError means Python couldn't even finish reading the file — so nothing runs at all, not one line, not even the correct lines above it. This is actually the friendly case: the error arrives before any work happens, and the line number it reports is the line with the stray colon on it. Go to that line, delete the colon, done.

The reverse mistake, which is easier to miss. Leaving a colon off a line that needs one:

for tool in tools print(tool)
SyntaxError: expected ':'

Newer Python versions name the missing character outright. Older ones just say invalid syntax and point at the line — so if you get a bare SyntaxError on a for/if/def line and can't see anything wrong with it, the colon is the first thing to check.

Why the colon exists at all. It's the marker that says "the indented lines below are the body of this." Python needs both the colon and the indentation — the colon announces a block is coming, the indentation marks how far it extends. They're a pair; that's why a colon on a line with nothing indented beneath it is also an error.

Nesting quotes

Quote-nesting rule: whatever quote type opens a string, the next one of that same type closes it — no exceptions, no "it knows what I mean."

If an f-string opens with ", using " again for a dict key inside it (f"{menu["large"]}") ends the string early at the first inner ", and everything after becomes broken code sitting outside any string. Fix: use the other quote type inside (f"{menu['large']}"). This isn't specific to f-strings — it's the same rule for any string containing a quote character, e.g. "it's fine" needs double quotes outside precisely because there's a single quote (apostrophe) inside.

Joining text and values

You can't glue a value onto a string with brackets — that's a function call, not printing two things together.

print("Final price:"(final_price)) # wrong — this errors

Putting (final_price) directly after the string makes Python think you're trying to call the string itself, like calling a function — and strings aren't callable, so it errors. To show text and a value together, either separate them with a comma, or use an f-string:

print("Final price:", final_price) print(f"Final price: {final_price}")
