Values and conversion

What kind of thing a value is, and turning one kind into another.

04chapter

01

Values and conversion

input() always hands back text

input() always returns a string — always, no exceptions.

Even if someone types 25 or y or 100, what lands in your variable is the text "25", "y", "100" — not a number, not a boolean. input("Age: ") + 1 will error, not add 1 to their age, because you're trying to add a number to a string. Anything you want to treat as a number needs int(...) or float(...) wrapped around the input first; anything you want to treat as true/false needs a comparison (== "y") to turn it into an actual boolean.

02

Values and conversion

int(input()) is wrapping, not sequence

int(input(...)) — wrapping, not sequence.

The temptation when this won't recall is to think of int and input as steps in a left-to-right order — one before the other on the line. They're not sequential, they're nested: input(...) is the inner function, int(...) is the outer function wrapped around it.

age = int(input("Enter your age: "))

Read it from the inside out: input("Enter your age: ") runs first — it shows the prompt and waits, then hands back whatever the person typed, as a string. int(...) then wraps around that whole result and converts the string to a number. age catches whatever comes out of the outer layer last.

Same shape as the outer/middle/inner box idea — input is the inner box doing the actual work of asking and catching a string; int is the outer box that takes what the inner box produced and converts it. Two functions, one open-bracket each, both closing brackets stacked at the end () )) — miscounting those closing brackets is the most common way this line breaks.

03

Values and conversion

range() takes integers only

range() requires an integer, not a float or anything else.

range(5) works, range(5.0) doesn't — even though Python is generally relaxed about mixing ints and floats elsewhere (e.g. 5 * 1.5 works fine). range() is specifically strict about this. Whole numbers only, no exceptions, in every position:

range(5) # fine range(1, 6) # fine range(1.5, 6) # TypeError
TypeError: 'float' object cannot be interpreted as an integer

Where this actually catches you. Rarely by typing 5.0 on purpose — almost always by feeding range() a variable that came from somewhere else and turned out to be a float:

  • straight from input() without conversion, or converted with float() instead of int()
  • the result of a division, because / always produces a float in Python, even when it divides evenly: 10 / 2 is 5.0, not 5

That second one is the sneaky one. range(10 / 2) errors, despite "five" being a perfectly good whole number, because the division handed back 5.0.

The fix in both cases is the same — wrap it in int():

count = int(input("How many? ")) # not float() range(int(10 / 2)) # or use // instead

// is floor division, which produces an integer directly: 10 // 2 is 5. If a division result is destined for range(), // saves you the conversion.

04

Values and conversion

Truthiness

There's no bool() shortcut for qualifying a yes/no answer — the comparison itself IS the qualification.

int(...) and float(...) genuinely convert text into a number of the same value — "25" becomes 25. bool(...) doesn't work the same way: it never looks at what's inside the string, it only asks "is this string empty or not?" Any non-empty text — "y", "n", "banana" — is True under bool(). So there's no wrapping function that turns a yes/no answer into a usable true/false the way int() turns a number-string into a number.

The real concept underneath this: before you can act on an answer, you have to state — explicitly, in the code — exactly what counts as a "yes." is_adult == "y" isn't just syntax, it's the moment the program commits to a definition of what a qualifying answer looks like. Skipping that and writing if is_adult: doesn't ask "did they say yes" — it only asks "did they type literally anything at all," which silently accepts every possible answer as if it qualified. This is worth remembering as a category, not just a fixed line of code: any time a question is being asked, decide and write down what a qualifying answer actually is, before doing anything with the response.

What if some_variable: is actually asking. It does not ask "did they say yes." It asks "is there anything in here at all."

answer = input("Member? (y/n): ") if answer: # True for "y". Also True for "n". print("Member discount applied")

Any non-empty string is truthy, so "n" passes this test just as happily as "y" — the person typed something, which is all the condition checks. The discount gets applied to everyone who doesn't just press Enter.

The values that are falsy — the complete list worth knowing:

"" # empty string 0 # zero, int or float [] # empty list {} # empty dict None False

Everything else is truthy. Note "0" and "False" are strings, and non-empty, so both are truthy — which is exactly the trap when they've come from input().

The fix is always the same: state the comparison.

if answer == "y": # now it asks the actual question

Where truthiness IS the right tool. It isn't wrong everywhere — it's wrong for testing what someone typed. It's correct for testing whether a collection has anything in it:

if bargain_shelf: # "did the loop find any?" print(bargain_shelf) else: print("Nothing under £10")

That reads well and is idiomatic Python. The distinction: truthiness answers "is there anything here?", never "is it this particular thing?"

Recurring trap. This surfaced across the membership gate, loyalty card and restaurant capstone drills — worth checking on every input-driven if from now on.

05

Values and conversion

len() depends what you feed it

len() measures "how many items," but what counts as an item depends entirely on what's handed to it.

Same function, different behaviour depending on the input type: fed a list, it counts entries (len(tools) → how many tools). Fed a string, it counts characters, since a string is just a sequence of characters underneath (len(tool) where tool is one word → how many letters in that word). No separate function needed for each — len() always means "count what's inside," the type of what's inside decides what "inside" means.

06

Values and conversion

% the remainder

% (modulo) gives the remainder after division — the standard way to test for even/odd, and divisibility generally.

number % 2 divides by 2 and returns whatever's left over — 0 if it divides evenly (even number), 1 if not (odd number). More generally, x % y == 0 asks "does x divide evenly by y" — works for any divisor, not just 2 (e.g. number % 3 == 0 tests divisibility by 3).

What it's actually doing — primary school long division, keeping the remainder and throwing the answer away:

17 % 5 # 5 goes into 17 three times, 2 left over → 2 20 % 5 # 5 goes into 20 four times, nothing over → 0 3 % 5 # 5 doesn't go into 3 at all, 3 left over → 3

That last one catches people: when the left number is smaller than the right, the whole thing is the remainder. Nothing was divided.

% is the twin of // (floor division), which keeps the answer and throws the remainder away. Between them they split a division in two:

17 // 5 # 3 — how many whole times 17 % 5 # 2 — what's left over

Where you'll actually use it. Even/odd is the textbook example but the least useful in practice. The real jobs:

JOB ONE — do something every Nth time through a loop.

for i, order in enumerate(orders, start=1): print(order) if i % 10 == 0: # every 10th row print("--- page break ---")

This is the one worth remembering. i % 10 == 0 is true at 10, 20, 30 — the counter resets to zero every tenth pass, which is exactly "every tenth time" expressed as a condition.

JOB TWO — splitting a total into units and remainder.

total_minutes = 145 hours = total_minutes // 60 # 2 minutes = total_minutes % 60 # 25 print(f"{hours}h {minutes}m") # 2h 25m

Same shape for pence into pounds and pence, items into full boxes plus leftovers. Any time a quantity needs breaking into a bigger unit plus what's left, it's // and % as a pair.

JOB THREE — wrapping a number back around to a fixed range.

day_number % 7 # always lands 0–6, whatever you feed it

Useful for cycling through a list repeatedly without running off the end — the result can never exceed the divisor minus one.

JOB FOUR — alternating.

if i % 2 == 0: row_colour = "grey" else: row_colour = "white"

Striped table rows, alternating anything. This is even/odd put to work.

The trap: % means something else entirely inside a string.

print(f"Discount: {rate}%") # just a percent sign, plain text print(17 % 5) # the operator, gives 2

Inside a string it's a literal character. Outside, it's arithmetic. Same symbol, unrelated jobs — the same pattern as the brackets in Chapter 02, and worth filing alongside it.

Negative numbers behave unusually, if you ever meet one. -1 % 5 gives 4 in Python, not -1. The result always takes the sign of the right-hand number, which is unusual among programming languages but is what makes the "wrapping" job above work cleanly. Not worth memorising — worth recognising if a result ever looks wrong.

07

Values and conversion

+= is still an assignment

+= is shorthand for "take what's already there, add to it, and store the result back in the same variable."

total_revenue += fee means exactly the same thing as total_revenue = total_revenue + fee — read the current value, add fee to it, save the result back into total_revenue. The shorthand form is just more compact; it doesn't skip any of those steps, it just avoids writing the variable's name twice on the same line. Same mechanism works for -=, *=, /= — each one means "current value, this operation, this amount, store it back."

Because it's an assignment, it counts as one everywhere. This is the part that catches people, and it is why the scope trap matters: += does not look like an assignment, but it is one, so it triggers every rule that applies to assignments.

  • Inside a function, total += x makes total local for the whole function, exactly as total = ... would. See The scope trap in Chapter 10 (Functions).
  • The variable must already exist before you can += to it, because the operation reads the current value first:
total += 5 # NameError if total was never created
NameError: name 'total' is not defined

This is the accumulator rule from the loop drills stated from the other direction — the reason you write total = 0 before the loop isn't ceremony, it's that += has nothing to read from otherwise.
