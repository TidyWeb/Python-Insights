Where elif sits

elif sits at the same indentation level as the if it belongs to — never nested one level inside it.

if coffee_type == "regular": ... elif coffee_type == "special": # same indent as the `if` above ...

if/elif/else are read by Python as one single decision block — they have to line up vertically. Indenting elif further in makes Python think it belongs to whatever inner block sits above it instead, which breaks the logic silently rather than throwing an obvious error every time.

Flipping a comparison

Flipping the comparison and flipping the branches cancels out — two "opposite-looking" conditions can be the exact same rule.

if how_many < 20: charge / else: free and if how_many >= 20: free / else: charge are not two different rules — they're the same rule written from two different starting points. < and >= are logical opposites of each other, and if/else are also opposites of each other; flip both at once and the meaning is preserved exactly. Getting a nagging feeling that < "should" be > after the code already produces the right answer is usually this — not a real error, just the same logic looked at from the other side.

The check that settles it, instead of doubting from memory: take the actual example values from the spec and trace them through the line exactly as written — don't reason about what the operator "should" be in the abstract. If how_many = 25 produces "free" and how_many = 4 produces "charge," and those match what the spec asked for, the code is correct, full stop — regardless of which operator or which branch felt right on first read. This is a reliable way to settle self-doubt about boundary conditions (< vs <= vs > vs >=) without having to re-derive the logic from scratch every time.
