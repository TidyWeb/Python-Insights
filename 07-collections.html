Collections

Chained lookups resolve inside-out

Chained lookups resolve inside-out, and that's what lets one variable do the work of several.

fee = membership_fees[member["tier"]] looks like one flat line, but Python resolves the innermost bracket first: member["tier"] runs, produces a plain string ("premium"), and only then does that result get used as the key for the outer lookup on membership_fees. The inner result never gets its own named variable — it exists just long enough to feed the next bracket out, then it's gone. Without this inside-out resolution, the same job would need a separate line and a separate throwaway variable for every layer (tier = member["tier"], then fee = membership_fees[tier]) — the chained version collapses that into one line by letting each bracket's result become the next bracket's input directly. fee ends up holding a real number, not any of the intermediate text it passed through to get there.

02

Collections

The positional slot rule

The positional slot rule — re-addressing beats "staying inside."

When pulling several values out of the same dictionary sitting inside a list, there's no way to look something up once and then keep asking follow-up questions about it. Every single value needs the full path spelled out again from scratch:

menu[5]["name"] menu[5]["price"]

Not menu[5] once and then ["name"] and ["price"] off the back of it as if Python remembers where you just were — it doesn't. Python has no concept of "still being inside" a lookup after the line finishes running. Each line is a fresh instruction, read fully, top to bottom, every time. It feels wrong because in spoken English, once you've said "the fifth item," you can just say "its name" and "its price" without repeating yourself — English carries context forward, Python doesn't.

The remedy: park the lookup in a variable, then reach into that.

You cannot make Python remember where you were — but you can hand the place you were to a variable, and that variable does persist across lines. This is the cure, and it is the thing that was missing from this note originally:

item = menu[5] # do the positional step ONCE print(item["name"]) # now reach into the parked thing print(item["price"])

item now holds the actual dictionary sitting at position 5. Every line after that reaches into item directly, and the [5] never needs writing again. Two lookups become one lookup plus two cheap reaches.

This is the same manoeuvre as English carrying context forward — you just have to do it explicitly, by naming the thing, instead of expecting Python to infer it.

In a loop, the loop variable does this job for you already.

for item in menu: print(item["name"], item["price"])

There is no positional step at all here. for item in menu: hands you one dictionary per pass, already parked in item — so the "address it fully every time" problem disappears entirely. This is worth noticing, because it means the re-addressing burden is mostly a symptom of reaching into a list by number rather than looping over it. If you find yourself writing menu[5]["name"] and menu[5]["price"] and menu[5]["size"] on three consecutive lines, that is the signal to either park it in a variable or use a loop.

When you genuinely do need the full path. Writing it out in full is correct and normal for a single one-off lookup — print(menu[5]["name"]) on its own needs no variable. The parking manoeuvre earns its place from the second lookup onward, not the first.

03

Collections

The stop number is exclusive

The stop number in a slice is exclusive — it marks where slicing stops, not the last item included.

orders[0:3] reads as "start at index 0, keep going, stop the moment you reach index 3" — so index 3 itself is never included, only 0, 1, and 2. To get the first three items, the stop number has to be one higher than the last index you actually want (three items → stop at 3, not 2). One way to frame it: the stop number acts like a buffer, stopping one short of itself.

The arithmetic that settles it every time. Rather than counting items on your fingers, subtract:

stop − start = how many items you get.

orders[0:3] # 3 − 0 = 3 items orders[2:5] # 5 − 2 = 3 items orders[1:2] # 2 − 1 = 1 item orders[4:4] # 4 − 4 = 0 items — an empty list, not an error

This works for any slice, always, and it's faster than reasoning about which index is or isn't included. If you want three items and the subtraction doesn't give you three, the numbers are wrong before you've run anything.

Why Python chose it this way — it's not arbitrary, and knowing the reason makes it stick. Two properties fall out of exclusive stops that would otherwise be fiddly:

tools[:2] + tools[2:] # == tools, exactly, no overlap, no gap

Splitting a list at any point needs only one number, used as both the stop of the first half and the start of the second. If stops were inclusive you'd need [:2] and [3:] and would have to remember the +1 every time.

The fence-post picture, if the arithmetic doesn't land. Think of the index numbers as sitting between the items rather than on them:

0 1 2 3 | a | b | c |

[0:3] means "cut at 0, cut at 3, take what's between" → a b c. Read this way the stop isn't excluding anything; it's just where the second cut goes. This is why [4:4] gives nothing — both cuts land in the same place.

The most common real error. Wanting "the first three" and writing the last index you want rather than the stop:

first_three = orders[0:2] # wrong — gives 2 items first_three = orders[0:3] # right — 3 − 0 = 3

And a shorthand worth knowing: a blank start means "from the beginning", so orders[:3] is the same thing, with one less number to get wrong.

04

Collections

Counting from the right

Negative slice indices still read left to right in list position — they just count from the right-hand end instead of the left — and the stop is still exclusive.

-2 sits to the left of -1 in actual list order (second-to-last, then last), so start:stop direction still holds the normal way. The trap: leaving the stop blank (orders[-2:]) means "go all the way to the end," but writing the stop as -1 (orders[-2:-1]) means "stop just before the last item" — which excludes the last item entirely. To grab the final two items of a list, the stop has to be left blank, not written as -1.

Both numbering systems, side by side. Every position has two valid names, and they refer to the same slot:

list: a b c d e from L: 0 1 2 3 4 from R: -5 -4 -3 -2 -1

So tools[-1] and tools[4] are the same item here. Negative indices exist for one reason: you can reach the end without knowing the length. tools[-1] is always the last item, whether the list has five entries or five hundred.

Why there's no -0. Zero already means "the first item", and -0 is just 0 in arithmetic, so it can't also mean "the last". That's why counting from the right starts at -1 rather than -0 — it isn't an inconsistency, it's the only number left. This is also the root of the -1 trap below.

The trap in full. As a start, -1 means the last item. As a stop, -1 means stop before the last item. Same number, opposite practical effect, because stops are still exclusive:

orders = ["a", "b", "c", "d", "e"] orders[-1] # "e" — as an index orders[-2:] # ["d", "e"] — last two, correct orders[-2:-1] # ["d"] — the trap, loses "e" orders[:-1] # ["a","b","c","d"] — everything except the last

The recipes, so you don't have to re-derive them.

items[-1] # last item items[-2] # second to last items[-3:] # last three items[:-1] # everything except the last items[1:-1] # everything except first and last

The pattern: to include the end, leave the stop blank. To exclude something from the end, put a negative number in the stop.

The one rule that carries over unchanged from the previous entry. The subtraction still works, once you convert to positive indices — but easier is simply this: if you want the slice to run to the end of the list, the stop must be empty. No number, negative or positive, will include the final item, because stops are always exclusive.

Mixing the two systems is legal. orders[1:-1] is fine — positive start, negative stop. Python doesn't mind; each number is resolved independently before the slice runs.
