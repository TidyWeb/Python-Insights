The plural name is finished with

FUNDAMENTAL RECURRING CONFUSION — reaching for the original collection name instead of the loop variable the for line just created.

The diagnosis: the instinct is to keep looking back at staff (the thing that "exists" up top) to find name, rather than recognising that for person in staff: already created a brand-new tool — person — that holds exactly one item, fresh, every pass. Once inside the loop, the loop variable (person, order, member, whatever it's called that pass) IS the thing to reach into for a key lookup — not the original list name. The original list (staff) doesn't need touching again inside the loop body at all; the loop already did that job. This is about trusting a freshly-created loop variable as the correct target, not just the singular/plural naming distinction. Watch for this resurfacing across any new loop context, not just dictionaries.

The tell, and the fix. The symptom is always the same shape: a line inside a loop body that mentions the plural name.

for person in staff: print(staff["name"]) # wrong — reaching past the loop variable print(person["name"]) # right — reaching into this pass's item

The first line errors, because staff is a list and "name" is not a valid list index. That error message — a list being asked for a string key — is the reliable signature of this exact mistake, so it is worth recognising on sight rather than reading as a mystery.

The habit that prevents it: once you write the for line, the plural name is finished with. It did its job by handing you the loop variable. Inside the loop body, if you find yourself typing the plural, stop — you almost certainly want the singular.

Naming the loop variable well makes this self-policing. for person in staff: makes the wrong line look obviously wrong. for s in staff: does not, which is one practical argument for spelling loop variables out in full.

enumerate()

enumerate() attaches a running position number to each item as it goes — it manufactures that number rather than finding it in the data.

What it does. enumerate() walks a collection and hands back each item with a running position number attached. It manufactures that pairing — the number does not come from inside the data, it is generated by enumerate as it counts along.

for i, tool in enumerate(["hammer", "saw"]): print(i, tool)
0 hammer 1 saw

When to use it — the trigger. A plain loop (for day in days:) already gives you each value in turn. enumerate earns its place only when the position number is about to be used for something, and in practice that means one thing: reaching into a second list at the same position.

for index, day in enumerate(days): print(day, movies[index]) # index used to reach into movies

That's the entire justification — cross-referencing two lists kept in sync by position. The rule:

Need the position number for a lookup elsewhere → enumerate. Just need each value → plain loop.

Reaching for it out of habit on every loop misses that trigger. In that same example, the inner loop for movie in movies[index]: does not use enumerate, and shouldn't — there's no second list to cross-reference, so the movie's value is all that's needed.

It always hands back exactly two things, and always in the same order: (position, item). Not three, not a configurable number — two.

for i, order in enumerate(orders): # as far as this line can go

You cannot add more names to that unpacking to also catch fields from inside order. Those fields aren't siblings produced by enumerate — they're keys sitting inside the dictionary order already holds. Pulling them out is a separate step on its own line inside the loop body, using ordinary dictionary lookup:

for i, order in enumerate(orders): print(i, order["type"], order["size"]) # lookups, not unpacking

The "pair" coincidence — worth being explicit about. A dictionary has key:value pairs. enumerate produces pairs. These are unrelated ideas that share a word.

enumerate doesn't need what you feed it to be "in pairs" already, and it never looks inside the items to extract anything. It works identically on a plain list of strings:

enumerate(["Alice", "Ben"]) # gives (0, "Alice"), (1, "Ben")

When members is a list of dictionaries, enumerate is pairing each whole dictionary with its position in the list — it is not reaching inside them for key:value pairs.

Naming and the start argument. i is the conventional name for the position number — not enforced by Python, but what you'll see everywhere, so worth recognising on sight. Counting begins at 0 by default; start=1 shifts it for human-facing output:

for i, tool in enumerate(tools, start=1): print(f"{i}. {tool}") # 1. hammer 2. saw

Output shaped like "1. hammer, 2. saw" is the signal that start=1 is wanted.

RELATED BUT SEPARATE — the box/shelf model for nested loops.

This isn't about enumerate; it's the mechanical picture underneath a nested loop, kept here because it belongs with the same idea.

One shelf, three boxes labelled Friday/Saturday/Sunday, cassettes inside each. Pull a box down, take the cassettes out one at a time until it's empty — however many happen to be inside, the inner loop never needs to know the count in advance — then put the empty box back and move to the next box along.

The thing worth holding onto: in the code, the label and the contents are not fused the way they are in that mental image. They're two separate lists (days and movies) that only line up because they sit at matching positions. Nothing in Python ties "Friday" to that specific set of films except that both happen to be at index 0 in their own list. index is the stand-in for "these two are the same box" — it is the only thing enforcing the pairing. If the two lists ever fell out of sync, the labels would point at the wrong contents, because nothing else connects them.
