The sealed room. What goes in, what comes out, and what stays private.

01

Functions

print versus return

print() shows something on screen but hands nothing back — a function with no return always gives back None.

def broken_double(n): print(n * 2) result = broken_double(5) # prints 10 print(result) # prints None

print and return do genuinely different jobs. print is for a human to look at; return is for the program to use the value afterward. A function can do both, either, or neither — but if you try to capture the result of a function that only prints, you get None, not the number you saw on screen.

02

Functions

The sealed room

FUNCTION SCOPE — a function is a sealed room.

Variables created inside a function only exist inside that function. Once the function finishes running, they're gone — nothing outside can see or use them. Variables created outside a function, at the top level, are visible everywhere, including inside functions. It only works one way: something made outside can be used inside (the outside can "shout in"), but something made inside stays trapped inside and disappears once the function ends — outside code can never reach in and grab it.

Indentation marks the boundary exactly the same way it does for if/for/else: a line indented under def some_function(): belongs to that function's block ("inside"); a line back at the left margin is "outside," in scope everywhere.

Important exception within this pattern: if/elif/else/for/ while blocks are NOT sealed rooms — they're organisational only. Variables created inside them are still visible on the left edge afterward, same global scope throughout. A function block is the only block type that seals — this is the one case where the usual "indented = sub-process, return to left edge for the result" reading doesn't fully apply.

03

Functions

The scope trap

Assigning to a variable name anywhere inside a function makes Python treat it as local for the entire function — even before that line runs.

total = 100 def spend(amount): total = total - amount # errors: UnboundLocalError return total

The mere presence of total = ... anywhere in the function body is enough for Python to decide total is local to that function, full stop — it does not quietly fall back to reading the outer total on the right-hand side first. This is why the function errors before it even gets to run the subtraction.

Spotting it before it bites. Python decides a variable is local at compile time, by scanning the whole function body for any assignment to that name — before a single line executes. So you can do the same scan yourself. For any name inside a function, ask two questions in this order:

1. Does this name get assigned to anywhere in this function? (=, +=, -=, or as a for loop variable — all count.) 2. Does a variable of the same name also exist outside?

Two yeses means you have this bug, and it will fire on whichever line reads that name first. One yes or none, and you are fine.

The reason += catches people out is that it does not look like an assignment. It is. total += amount is total = total + amount wearing a disguise, so it triggers the local decision exactly the same way.

Fix A — pass in, return out. This is the default.

total = 100 def spend(amount, current_total): return current_total - amount total = spend(20, total) # reassign on the outside print(total) # 80

The function no longer knows or cares that an outer total exists. It receives a number, produces a number, and the caller decides what to do with the result. Everything the function depends on is visible in its own brackets, which is why this is the version to reach for by default.

Note the shape of the last call: total = spend(...). The function cannot change total for you, so you do the reassignment, on the outside, using what it handed back.

Fix B — rename the local so there is no clash at all.

Sometimes you genuinely do want a fresh local variable and you only tripped over this because you reused a name by accident.

takings = 100 def daily_report(sales): running = 0 # a new name, nothing outside is called this for sale in sales: running += sale return running print(daily_report([10, 20, 30])) # 60 print(takings) # 100, untouched

No error, because running clashes with nothing. Half the time this bug is not a scope problem at all — it is a naming collision, and the cheapest fix is a different name.

Fix C — global. Know it, avoid it.

takings = 0 def add_sale(amount): global takings # "use the outer one, don't make a local" takings += amount add_sale(15) add_sale(20) print(takings) # 35

This works and you will see it in other people's code, so you need to recognise it. The reason to avoid it: the function now has a hidden dependency. Reading add_sale(15) on its own tells you nothing about what it changes — you have to go and read the body to find out it quietly reaches out and edits takings. With Fix A, the call site tells you everything. Learn global so you can read it; reach for Fix A when you write.

The case that works fine, for contrast.

Reading an outer variable is never a problem. It is only assigning that triggers the local decision.

shop_name = "Ravi's Coffee" def banner(): print(f"Welcome to {shop_name}") # read only — fine banner()

Nothing in banner assigns to shop_name, so Python never marks it local, and the outer one is found without any special handling. This is worth holding onto, because it means you do not need to pass everything in as a parameter — only the things you intend to change.

04

Functions

return versus global

TWO PIPELINES OUT OF A FUNCTION'S SEALED ROOM — return vs global.

return is a passive pipeline: the function hands a value out, but whoever called it has to actively catch it (store it in a variable, or wrap the call in print()) or the value is lost. Nothing outside is changed by return alone.

global is an active pipeline in the other direction: written as global some_name inside a function, it tells Python "don't create a new local variable — reach out and edit the real outside one directly." Without it, assigning to a name that matches an outside variable silently creates a separate, sealed, local copy instead — looks like an update, isn't one.

Two different tools, two different directions: return sends a value out on request; global reaches out and changes something that already exists outside.

What "the value is lost" actually looks like. This is the failure the word "passive" is warning about, and it's silent — no error, no warning, nothing:

def double(n): return n * 2 double(5) # runs, returns 10, and the 10 vanishes print("done")

Output is just done. The function ran. It calculated 10. It handed 10 back. And because nothing was waiting to catch it, Python threw it away.

The three ways to catch it. There is no fourth:

result = double(5) # 1. store it in a variable print(double(5)) # 2. feed it straight into something else total = double(5) + 1 # 3. use it directly in an expression

All three work because in each one, the returned value has somewhere to land. A bare double(5) on its own line has nowhere.

Why this is worth watching for specifically. A function that only prints works fine when called bare — greet() on its own line does its job. So the habit of calling functions bare is correct, right up until the function starts returning instead of printing, at which point the same habit silently discards the answer. The switch from print-functions to return-functions is exactly where this bites.

The question to ask of every call you write: does this function print its result, or return it? If it returns, the call must appear on the right-hand side of an =, or inside something else. If it prints, a bare call is correct.

05

Functions

Default parameters

DEFAULT PARAMETER VALUES — a fallback so the function never breaks from a missing argument.

def serve_dish(name, dish="pasta", spice_level="medium"): — the ="pasta" and ="medium" aren't assignments happening now, they're fallback values sitting ready. Without a default, every parameter is mandatory — leave one out of a call and Python throws a hard error, no exceptions. With a default, that parameter becomes optional: if a call doesn't supply it, Python quietly uses the fallback instead, and the function still runs successfully rather than breaking.

Defaults only matter for calls that omit something. A call that supplies every value overrides every default and behaves identically whether defaults exist or not — the whole point of a default is to keep the function usable even when information is missing, not to change behaviour when it isn't.

06

Functions

The slot model

THE "SLOT" MODEL — parameters are numbered slots in the def line, filled either by count (positional) or by label (keyword).

def book_table(name, time="7pm", guests=2): creates three slots in a fixed order: slot 1 = name, slot 2 = time, slot 3 = guests. No parameter is inherently "the positional one" or "the keyword one" — any slot can be filled either way, depending purely on how that particular call writes it.

  • Positional fill: no label, matched purely by counting position left to right — "this is the next unfilled slot in order."
  • Keyword fill: labelled with name=, matched directly to that slot regardless of position, no counting involved.

Why mixing them backwards breaks: once a call uses a label, Python stops counting positional slots. Any unlabelled value that shows up after a labelled one has no reliable slot left to land in, because the count was abandoned partway through. The error is about the order of labelled vs unlabelled arguments in the call, not about which specific parameter is involved.

07

Functions

The keyword argument order rule

HARD RULE — once a call switches to keyword arguments, everything after must also be keyword. No going back to positional.

book_table("Ravi", guests=4) — fine. Positional first ("Ravi" fills name by slot), keyword after (guests=4 by label). Nothing positional comes after the keyword one.

book_table(guests=4, "Ravi") — SyntaxError. Once guests=4 breaks the left-to-right count by naming itself, Python has no reliable way to know what slot the next unlabelled value ("Ravi") should fill — the count that positional relies on is already broken.

Rule of thumb: positional first for the obvious values, keyword after for anything further along or being set apart from a default. Not a style choice — get the order backwards and the program won't run at all, not just misbehave silently.
