Decorators

Functions that wrap other functions, and the one place execution order stops being top-to-bottom.

11chapter

01

Decorators

The parcel analogy

A decorator is a box that receives another function as an unopened parcel, builds a new box around it, and hands the new box back — under the original function's name.

Here is the whole thing first. Every name discussed below comes from these twelve lines, so it is worth having them in front of you.

def add_lights(func): def wrapper(): print("Untangling the lights") func() print("Switching them on") return wrapper @add_lights def decorate_tree(): print("Hanging the baubles") decorate_tree()
Untangling the lights Hanging the baubles Switching them on

Three things print, but only one of them was written inside decorate_tree. The other two came from add_lights, which decorate_tree never calls and never mentions.

The four moves, in order.

1. The inbox slot. def add_lights(func): — func is just a parameter name like any other. It is not a keyword and carries no special meaning to Python; it is simply the slot this box uses for incoming parcels. It could be called parcel and nothing would change.

2. The posting. @add_lights sitting above def decorate_tree(): triggers this behind the scenes: the whole decorate_tree parcel — unopened, contents untouched — gets posted into add_lights, landing in the func slot.

3. The new box is built around it. Inside add_lights, a new box called wrapper is built around that parcel. wrapper can see func because it is nested inside add_lights — the same reachability rule as any nested scope. Its job is: print something, open the func parcel with func(), then print something else. The brackets on func() mean "open this parcel and let its contents run".

4. The swap. add_lights returns wrapper itself — unopened, not yet run — and the name decorate_tree is quietly repointed at this new wrapper box instead of the original plain parcel.

So decorate_tree() on the last line no longer opens the original parcel directly. It opens wrapper, which opens the original parcel through func(), partway through its own instructions. That is why two lines you never asked for appear around the one you did.

02

Decorators

Why they feel backwards

WHY DECORATORS FEEL BACKWARDS — execution order isn't top-to-bottom reading order.

Normal reading (left to right, top to bottom) doesn't match how a decorated function actually executes. The @decorator line sits above the function it modifies, but its effect (swapping the name to point at wrapper) only takes hold once the whole definition is processed — and the actual sequence of what prints, in what order, depends on lines written last (func(), buried inside wrapper, itself defined inside add_lights, defined before decorate_tree even exists) reaching back to affect something that appears later in the file. Spotting this takes deliberately tracing the call order separately from the reading order — the two aren't the same thing here, unlike straightforward top-to-bottom code.

Reassurance: indentation and block structure still work exactly as normal throughout all of this — add_lights, wrapper, and decorate_tree are each still clearly delimited by indentation, same rules as ever. It's specifically execution order that stops matching read order, not the structural rules already relied on. A bare some_function() sitting on its own line, anywhere, is always a live instruction to run that function now — not just a label or a reference — worth remembering, since that's what made decorate_tree() at the bottom easy to misread as inert.

THE TRACE — the remedy for the backwards feeling.

Describing the mechanism isn't enough to stop it feeling wrong. The thing that fixes it is doing this trace once, slowly, on paper. Here is the whole program, with every line numbered:

1 def add_lights(func): 2 def wrapper(): 3 print("Untangling the lights") 4 func() 5 print("Switching them on") 6 return wrapper 7 8 @add_lights 9 def decorate_tree(): 10 print("Hanging the baubles") 11 12 decorate_tree()

Output:

Untangling the lights Hanging the baubles Switching them on

Now the order Python actually runs those lines in:

1. Line 1 — Python reads def add_lights. It does not run the body. It just learns the recipe and moves on. 2. Line 8–9 — Python reads def decorate_tree and learns that recipe too. Still nothing has run. 3. Line 8 — the @add_lights line now fires. This is the moment the swap happens. Python calls add_lights(decorate_tree), passing the original function in as the parcel. 4. Inside add_lights, line 2 defines wrapper — again, learns the recipe, doesn't run it. Line 6 returns wrapper back out. 5. The name decorate_tree is now quietly repointed at wrapper. The original function still exists, but only wrapper knows how to reach it, through the func slot. 6. Line 12 — decorate_tree() runs. But decorate_tree is now wrapper, so this runs wrapper's body. 7. Line 3 prints "Untangling the lights". 8. Line 4 — func() opens the original parcel. Line 10 prints "Hanging the baubles". 9. Line 5 prints "Switching them on".

Where the backwards feeling actually comes from. Steps 1 to 5 all happen before any output appears at all. Everything above line 12 is Python quietly rearranging who points at what — no printing, no visible activity. Then line 12 fires and all three prints happen in a burst, in an order determined by code written above the thing that triggered it.

So the read order and the run order genuinely are different, and you weren't imagining it. The fix isn't to make it feel top-to-bottom again — it's to read a decorated function in two passes:

  • Pass one — setup. Ignore all bodies. Just ask: which name ends up pointing at which function? (Answer here: decorate_tree now points at wrapper.)
  • Pass two — execution. Start at the call at the bottom, and follow only the name you established in pass one. Read wrapper's body top to bottom as ordinary code, and treat func() as "the original function runs here."

Pass two is top-to-bottom, ordinary, and unsurprising. All the strangeness lives in pass one, and pass one produces exactly one fact: a name got repointed. Separate those two passes and the mind- flip stops.

The single sentence to hold onto. @decorator does not change the function — it replaces the name with a new function that has the original one tucked inside it.
